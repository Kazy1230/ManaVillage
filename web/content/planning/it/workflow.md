# IT を学ぶ(日本語で書く)の記事制作ルール

Git、ネットワーク、データベースなど、IT の仕組みを、身近なたとえと図で解説する記事(`/it/articles/...`)のルール。
**流れと役割分担は `planning/common.md`**(2-1c, 2-1d の書き方も同じ)。記事の作業をするときは、`common.md` とこの文書の2つを読む。

## 1. 読者と、基本の方針

- 読者: IT を使い始めた人、これから学ぶ人(初心者〜初級)。記事ごとに想定読者を決める
- 著者: **Kaz**(`author: kaz`)。白河雪菜は、英語学習・日本語学習の記事だけで使う
- type: 基本は **general**。体験談は、personal-brain と `content/materials/` に記録があるものだけ(`common.md` 2-1b)。**仕事の内容(勤務先、顧客、業務の細部)は、体験談として書かない**
- 分量の目安: 2,500〜4,500字(内容が足りなければ短くてよい)
- 見出し・導入・口調・改行は `common.md` 2-1d。仕組みは、**身近なたとえ**と**図**で見せる。たとえは、仕組みと対応していること(「ノートに書く = commit」「共有フォルダに置く = push」のように、1つずつ対応する)

## 2. 事実の根拠

- **公式のドキュメントを根拠にする**(例: Git は Pro Git、Web は MDN、各製品の公式ドキュメント、RFC)。確認できた内容と URL を、`sources` に書く
- コマンドや設定の例は、**書いた通りに動くか**を確かめる(可能なら実行する)。バージョンやOSで違う所は、そう書く
- 根拠にしない: 他の学習ブログ、Q&A サイト、AI の答え

## 3. ハブとタグ(固定の一覧。足したいときは Kaz に確認)

- **ハブ**(記事ごとに1つ): `Git`、`ネットワーク`、`データベース`、`Web の基本`、`開発ツール`
- **タグ**(3〜5個): ハブ名のほか、`初心者`、`開発ツール`、`セキュリティ`、`コマンド`、`用語`

## 4. 確認で足す項目(`manavillage-checker`)

- コマンド・コード例が、公式の記述と合っているか。実行して動くか
- たとえが、仕組みと対応しているか。たとえが、誤解を生まないか(例: 「ノートに書く」を、push と取り違えないか)
- 用語の定義が正確か。バージョン依存の記述に、断りがあるか
- 初心者がつまずく所(エラーの意味、よくある状況)に、答えているか

## 5. frontmatter

`planning/workflow.md` 6章と同じ。`hub`、`tags` は上の一覧から。`keyword` は、カードに大きく出る短い言葉(コマンド名など)。

## 6. 置き場所

| 項目 | 場所 |
|---|---|
| 記事 | `web/content/it/articles/<slug>.md` |
| テーマ管理表(IDは `I-xxxx`) | `web/content/planning/it/topic-map.md`(次の候補も、ここ) |
| イラスト | `web/content/illustrations/<slug>/` |

## 7. 新しい流れと書き方(2026-10-05 から)

`common.md` の 2-0(インタビュー → 記事化 → 面白くする編集者 → 承認 → 公開)と 2-1d(書き方)に従う。IT で特に守ること:

- **インタビューで聞くこと**: そのツール・仕組みで、最初に引っかかった所(困ったことが「ない」場合は、なぜ困らなかったか)。実際に使う場面。おすすめの使い方と、避けたい使い方。たとえるなら何か。仕事の内容(勤務先、顧客、業務の細部)は聞かない・書かない
- **コマンドと出力は、実機で動かして確かめる**。出力は、1回の実行でそろえて取る(ハッシュ値などを、別々の実行から混ぜない)。編集者は、コードブロックの中身を変えない
- **たとえは、仕組みの全工程に対応させる**(荷物の玄関=fetch、部屋=pull のように、add・commit・push・fetch・merge のどこまで対応するかを、決めておく)。対応しない部分を、無理にたとえない
- 設定やバージョンで挙動が変わるもの(pull.rebase など)は、「ふつうの設定では」と、本文の中で自然に断る
