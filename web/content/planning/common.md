# まなビレッジ 記事制作の共通ルール

どの科目の記事にも共通する、制作のルールと流れ。科目ごとのルールは、それぞれの文書に書く。

| 科目 | 科目の文書 | 記事のフォルダ | 在庫 | テーマ管理表 |
|---|---|---|---|---|
| 英語学習(日本語で書く) | `planning/workflow.md` | `content/articles/` | `planning/inventory.csv` | `planning/topic-map.md` |
| 日本語学習(英語で書く) | `planning/japanese/workflow.md` | `content/japanese/articles/` | `planning/japanese/inventory.csv` | `planning/japanese/topic-map.md` |

**記事を作るときは、この文書と、その科目の文書の2つだけを読む。** ほかの科目の文書は読まない(関係のないルールが混ざるため)。

---

## 0. 目的と大原則

- サイトのテーマは「学び、つまずき、助け合う」。読者が「分かった」と感じる記事を作る
- 目的は記事数を増やすことではなく、**他のサイトにない価値のある記事を、続けて出すこと**
- Google のスケールドコンテンツ・スパム(価値の薄い大量生産)に当たる記事は作らない
- ペース: **毎日、科目ごとに1本**(英語学習1本・日本語学習1本。2026-10-02 Kaz 決定)。品質に問題が出たら減らす
- **1つの検索意図に、1記事**(1章)
- 水増しをしない。内容が足りないなら、短くてよい

### 絶対に守ること

1. **体験談を捏造しない**。運営者の学習の方法・成果・経歴は、素材庫(personal-brain と `content/materials/`)にあるものだけ使う。どの科目で体験談を使ってよいかは、科目の文書に書く
2. **根拠のない断定をしない**。研究・統計・文法の説明は、確認できた出典があるものだけ書く。確認できなければ削る
3. **自分が書いた記事を、自分でチェックしない**。チェックは別のエージェント(別セッション)が行う
4. **公開(デプロイ)は Kaz の承認後だけ**。自動公開しない

## 1. テーマ管理と重複(カニバリ)

- 同じ検索キーワード・同じ意図を狙う記事が複数あると、記事どうしが順位を奪い合う。だから、科目ごとのテーマ管理表(topic-map)で管理する
- **在庫**(inventory.csv)は、扱うべき項目を全部書き出したリスト。**topic-map** は、アウトライン以降に進んだ記事の表
- topic-map に書くこと(記事ごとに1行): ID、タイトル、slug、主キーワード(ただ1つの検索語)、検索意図、想定読者、type、状態、ハブ
- 状態: `outlined` → `draft` → `published`。在庫の行は `idea` → `selected`(選んだら slug を書く)
- 記事を統合・削除したときは、行を直し、旧 URL から新 URL へリダイレクトする

**重複の判定基準**

- 見るのは、読者の設定ではなく、**検索意図が違うかどうか**
- 判定の質問: 「Aの検索語で来た人が、Bを読んで満足するか」。満足する → 重複(統合するか、どちらかを作らない)。満足しない → 別の記事にしてよい
- 読者だけ変えて、検索語も中身もほぼ同じなら、別記事にしない。読者で分けてよい条件は 2-1

**ハブ記事**

- 近いテーマの記事は、1つのまとまり(ハブ)として内部リンクで結ぶ
- ハブ記事は、まとまりの記事が3〜4本たまってから作る。ハブ記事の主キーワードは広めの語、個別記事はより具体的な語

## 2. 制作の流れ

```
[毎日・科目ごとに1本] 在庫から無作為にテーマを選ぶ(Kaz の確認なし)
  → アウトライン → 企画チェック(別エージェント)
  → 本文とイラスト → 機械チェック(check-article.mjs) → 本文チェック(別エージェント)
  → 下書き保存 → Kaz が確認(毎日2本) → 承認されたら公開
```

**Kaz が確認するのは、完成した記事だけ**(2026-10-02 決定)。テーマの承認はしない。テーマの良し悪しは企画チェックが判定する。

### 2-1. テーマを選ぶ(無作為。Kaz の確認なし)

- その科目の在庫の `status: idea` の行から、**無作為に1つ選ぶ**(`node scripts/pick-topic.mjs <english|japanese>`。2026-10-02 Kaz 決定。順番を決めると、同じ分類ばかりが続くため)
- 選んだら、topic-map を読んで重複を確かめる。重複するなら、その行の `note` に理由を書いて `status: skip` にし、選び直す
- 企画チェックで「勝てない」「書く価値がない」と判定されたテーマも、`skip` にして選び直す
- **読者違いの記事**(例:「英単語 覚え方 中学生」)を作ってよいのは、(1) 検索の言葉が実際に違い(サジェストにその組み合わせが出る)、(2) 中身が「使える時間・目的とゴール・使う教材・1日のスケジュール・つまずく場面」のうち3つ以上変わるときだけ。満たさなければ、元の記事に読者別の節を足す。読者違いの記事は、元の記事と互いにリンクする
- **似た言葉・フレーズは4つの層**でカバーする: ① 似た単語、② 機能の言い換え(依頼・断り・謝罪など、同じ目的を果たす言い方)、③ 丁寧さ・場面の違い(くだけた〜丁寧、話し言葉と書き言葉、確信度)、④ 母語からのずれ。記事は検索の言葉で「機能のハブ(言い方の一覧)→ 2〜3語の比較 → 1つの言い方」に分け、互いにリンクする
- 在庫が足りないときは、在庫そのものを増やす(`.claude/skills/manavillage-weekly`)

### 2-2. アウトライン

`planning/outlines/<slug>.md`(日本語学習は `planning/japanese/outlines/`)に作る。

- **決まった見出し構成(型)は使わない**(2026-10-02 Kaz 決定)。構成は、テーマと読者と検索意図に合わせて、毎回ゼロから考える。同じ型の記事ばかりになると、読んでいてつまらないため
- 作る前に、**同じ科目の直近5本の記事の見出しを読み**、流れが似すぎないようにする
- アウトラインに書くこと(中身。順番や見出しの形は自由):
  - 主キーワード、検索意図、想定読者
  - 見出し構成(h2, h3)
  - 主張ごとの具体例(例文、失敗例と正解例の対比、つまずく場面など)
  - 例え話と小ネタの案(2-4 のルール)
  - **上位記事にない情報**の候補(最低1つ。主キーワードで実際に検索して、上位の記事と比べる)
  - 根拠にする出典の候補
  - サムネ(核のイラスト)の内容と、本文に置くイラストの案(必要なところに、必要なだけ)
  - 内部リンク先(公開済みの記事だけ)

### 2-3. 企画チェック(共通の項目)

別のエージェントが判定する。**1つでも不合格なら差し戻し**(差し戻しは最大2回)。科目の文書の「企画チェックで足す項目」も判定する。

- [ ] 独自の切り口が具体的か。上位記事にない情報の候補があるか(実際に検索して確かめる)
- [ ] **勝てるか**: 上位が大手や公式で埋まっていて、切り口を変えても勝てない語ではないか
- [ ] topic-map の他の記事と、主キーワード・検索意図が被っていないか
- [ ] **同じ科目の直近5本と、構成(見出しの流れ)が似すぎていないか**
- [ ] 各主張に具体例があるか。例え話が、説明する仕組みと対応しているか
- [ ] サムネだけで、記事の核の概念が伝わるか。本文のイラストの案が、説明の助けになっているか(飾りだけの絵がないか)
- [ ] 出典の候補を、確認する計画があるか

### 2-4. 本文とイラスト(共通の書き方)

- 口調は、説教的でなく、親しみやすく。読者に呼びかけてよい
- 導入は短く。最初の数行で、この記事で何が分かるかを示す
- 1つの主張に、最低1つの具体例
- まとめで本文を繰り返さない。次に何をすればよいかを示し、コメントを誘う一言で終える
- 水増しをしない(同じ主張の言い換え、長い前置き)

**例えのルール**

- 誰にでもある、親近感の湧く日常の場面を使う(学校、通勤、コンビニ、スマホ、友達、家族、ご飯など)。科目の読者が想像できる場面にする
- 手本:「一目ぼれした人より、毎日会う幼馴染のほうが覚えているよね？単語も一緒」(単語 = 人、繰り返し触れる = 毎日会う、覚える = 覚えている。伝えたい仕組みと合っている)
- 説明したい仕組みと対応させる。面白くても、仕組みが違う例えは使わない
- 1つの主張に、例えは1つ。凝った例えを重ねない
- 特定の属性(性別、国籍、職業など)を、揶揄したり決めつけたりしない
- たとえ話として書く。効果の裏付けのように見せない
- 核になるイラストに使ってよい

**小ネタのルール**

- 他愛のない、誰にでもある日常の場面は、事実でなくてよい(「何もない所で躓くことありますよね」)。目安は各セクションに1つ。基本は読者に呼びかける形
- **小ネタに使ってはいけないもの**: 学習の成果や効果の裏付けになる話、数字(点数・期間・語数・回数)、資格や経歴、実在の人物・店・商品の名前、誰かを傷つける話
- 小ネタを、記事の主張の根拠にしない

**イラスト**(2026-10-02 Kaz 決定: 1枚に限らない)

- **サムネ(核のイラスト)**: 記事ごとに1枚。文章を読まなくても、記事の核の概念が伝わる図にする。記事一覧のカードと共有画像に使われ、**記事ページでは、タイトルと本文の間に自動で表示される**(どの科目も同じ)。本文には書かない(書くと2回出るので、機械チェックが不合格にする)
- **本文のイラスト**: 枚数は決めない。説明に図があったほうが分かるところに、必要なだけ置く(仕組みの図、比べる図、手順の図など)。飾りだけの絵は置かない
- 白い背景に、3歳児が描いたようなゆるい絵。画風はサイト全体で統一(`scripts/doodle.mjs`)
- webp で軽く。`alt` に、図が伝える内容を書く

### 2-5. 機械チェック

- `web/` で `node scripts/check-article.mjs <slug>` を実行し、合格(終了コード0)になるまで直す。科目は記事のフォルダから自動で決まる
- 何を機械で見るかは、科目の文書の「機械チェック」に書く

### 2-6. 本文チェック(共通の項目)

別のエージェントが判定する。**差し戻しは最大2回**。2回で合格しなければ、Kaz に判断を仰ぐ。科目の文書の「本文チェックで足す項目」も判定する。

**薄さ**

- [ ] 上位記事に書かれていない情報が、最低1つあるか(何かを明記させる)
- [ ] 具体例が、主張ごとに最低1つあるか
- [ ] 削っても読者が困らない段落、抽象論だけの段落がないか(あれば削除を指示)
- [ ] 構成が、検索上位の記事とも、同じ科目の直近5本とも、そっくりでないか

**事実**

- [ ] 文法・語法の説明に誤りがないか
- [ ] 研究・統計・文法の説明に、確認できる出典があるか(確認できないものは削除)

**捏造と小ネタ**

- [ ] 体験談が素材庫にあるものだけか(実際に検索して確かめる)
- [ ] 小ネタが、他愛のない日常の場面だけか。主張の根拠に使っていないか
- [ ] 例えが、効果の裏付けのように書かれていないか

**SEO**

- [ ] frontmatter がすべて埋まっているか。title と description が記事ごとに固有か
- [ ] h1 が1つで、h2・h3 が階層になっているか。すべてのイラストに、図が伝える内容の alt があるか
- [ ] 主キーワードが、title と導入に入っているか
- [ ] 内部リンクが張られているか(科目の公開済み記事が少ないうちは、本数を問わない)

### 2-7. 下書き保存とレビュー

- 合格した記事は `status: draft` で保存する(本番には出ない)。topic-map の状態を `draft` にする
- Kaz が、完成した記事を毎日2本(科目ごとに1本)確認する。ローカル(`npm run dev`)で記事の URL を開いてもらう
- 承認された記事だけ、`status: published` と `publishedAt` を書いてデプロイする。topic-map を `published` にする

## 3. 技術的な SEO とタグ(サイト全体)

- sitemap は、公開済みの記事と、検索に出してよいタグページだけを含む。下書きは含めない
- 各記事に、canonical、OG タグ、JSON-LD(`BlogPosting`、`BreadcrumbList`)を出す
- タグページは、記事が3本未満のあいだ、またはハブ記事があるテーマでは `noindex`
- タグは分類のためのもの。科目ごとの一覧から選び、1記事に3〜5個。主キーワードをそのままタグにしない
- 掲示板: 返信ゼロのスレッドは `noindex`

## 4. 見直し(Search Console)

Kaz が Search Console の数字を共有したときに行う。

- 「クロール済み・インデックス未登録」が増えている → 薄さのサイン。チェックの基準を厳しくし、必要なら本数を減らす
- 同じ検索クエリに、自サイトの複数のページが出ている → 1章の基準で、統合するか差別化する
- まとまりの記事が3〜4本たまったハブは、ハブ記事を作る
- 表示が多いのに順位が低い語は、記事の書き直しの候補にする。まだ記事のない語で表示が出ていたら、在庫に足す
