# まなビレッジ 記事制作の共通ルール(Kaz が書く版)

**2026-10-04 から、記事の本文は Kaz が書く。** Claude は、テーマと構成の提案、事実・出典の確認、チェック、イラスト、公開作業を行う。**Kaz の記事では、Claude は本文を書かない・書き直さない。**(それまでは、Claude が記事を書く完全自動のフローだった。経緯は `docs/04-history.md`)

**著者は二人**(2026-10-04 決定): Kaz と、アンバサダー「白河雪菜」。雪菜の記事は、Claude が雪菜になりきって書く(5章)。署名は記事ごとに分ける(Kaz の記事は「Kaz」、雪菜の記事は「白河雪菜(アンバサダー)」)。**どちらの記事でも、体験談は Kaz の本当の体験だけ**(捏造しない)。

どの科目の記事にも共通するルールと流れ。科目ごとのルールは、それぞれの文書に書く。

| 科目 | 科目の文書 | 記事のフォルダ | 在庫 | テーマ管理表 |
|---|---|---|---|---|
| 英語学習(日本語で書く) | `planning/workflow.md` | `content/articles/` | `planning/inventory.csv` | `planning/topic-map.md` |
| 日本語学習(英語で書く) | `planning/japanese/workflow.md` | `content/japanese/articles/` | `planning/japanese/inventory.csv` | `planning/japanese/topic-map.md` |

**記事の作業をするときは、この文書と、その科目の文書の2つだけを読む。**

---

## 0. 原則

- サイトのテーマは「学び、つまずき、助け合う」。読者が「分かった」と感じる記事を出す
- 目的は記事数を増やすことではなく、**他のサイトにない価値のある記事を、続けて出すこと**。Google のスケールドコンテンツ・スパム(価値の薄い大量生産)に当たる記事は出さない
- ペースは Kaz が決める。Claude は、Kaz が言ったときに提案を出す
- **1つの検索意図に、1記事**(1章)

### 役割分担

| | Kaz | Claude |
|---|---|---|
| テーマ | 提案から選ぶ(合わなければ引き直し) | 在庫から無作為に抽出し、調べて提案する |
| 構成 | 提案を見て、自分で変えてよい | 概要と構成を提案する(決まった型は使わない) |
| 本文 | **書く** | 書かない・直さない |
| 確認 | 指摘を見て、自分で直す | 機械チェック、事実・出典の確認、読みやすさ・薄さの指摘 |
| イラスト | 欲しい所に印を付ける | サムネと本文の図を描く |
| 公開 | **承認する**(承認後に、Claude がデプロイ) | 公開作業、記録の更新 |

### 絶対に守ること

1. **Kaz の記事では、Claude は本文を書かない・書き直さない**。指摘は「どこが、なぜ」を伝えるだけで、直した文を出さない。機械的な作業(frontmatter の組み立て、ルビの記法への変換など)は、Claude が行ってよいが、言葉は変えない。**体験談を、Claude が作ることはしない**(Kaz の記事でも、雪菜の記事でも)。雪菜の記事だけは、Claude が書く(5章)
2. **根拠のない断定は載せない**。研究・統計・文法の説明は、確認できた出典があるものだけ。Claude は、Kaz が書いた主張を原典で確かめ、確認できないものを指摘する。直すか削るかは Kaz が決める
3. **公開(デプロイ)は Kaz の承認後だけ**

## 1. 在庫と重複(カニバリ)

- **在庫**(`inventory.csv`)は、扱うべき項目を全部書き出したリスト。**topic-map** は、提案以降に進んだ記事の表
- 同じ検索キーワード・同じ意図を狙う記事が複数あると、順位を奪い合う。だから topic-map で管理し、提案の前に確かめる
- topic-map の1行: ID、タイトル、slug、主キーワード(ただ1つの検索語)、検索意図、想定読者、type、状態、ハブ。状態は `proposed`(提案済み) → `writing`(Kaz が執筆中) → `draft`(チェック済みの下書き) → `published`。在庫の行は `idea` → `selected`(提案したら slug を書く)/ `skip`
- **重複の判定**: 見るのは検索意図。「Aの検索語で来た人が、Bを読んで満足するか」。満足する → 重複(統合するか、どちらかを出さない)。読者だけ変えて、検索語も中身もほぼ同じなら、別記事にしない
- **読者違いの記事**(例:「英単語 覚え方 中学生」)を出してよいのは、(1) 検索の言葉が実際に違い(サジェストにその組み合わせが出る)、(2) 中身が「使える時間・目的とゴール・使う教材・1日のスケジュール・つまずく場面」のうち3つ以上変わるときだけ。満たさなければ、元の記事に読者別の節を足す。読者違いの記事は、元の記事と互いにリンクする
- **似た言葉・フレーズは4つの層**でカバーする: ① 似た単語、② 機能の言い換え(依頼・断り・謝罪など、同じ目的を果たす言い方)、③ 丁寧さ・場面の違い、④ 母語からのずれ。「機能のハブ(言い方の一覧)→ 2〜3語の比較 → 1つの言い方」に分け、互いにリンクする
- **ハブ記事**は、まとまりの記事が3〜4本たまってから。ハブ記事の主キーワードは広めの語、個別記事はより具体的な語
- 記事を統合・削除したときは、topic-map の記録欄に書く

## 2. 制作の流れ

```
Kaz:「テーマを出して」(科目と本数を言ってもよい。言わなければ、各科目3テーマ)
  ↓
Claude: 在庫から無作為に抽出 → 重複を確認 → 上位記事と出典を調べる → 提案を出す(2-1)
  ↓
Kaz: 1つ選ぶ(合わなければ引き直し)。構成は自分で変えてよい
  ↓
Kaz: 書く → チャットに貼る
  ↓
Claude: 下書きとして保存 → 機械チェック → 事実・出典の確認 → 読みやすさ・薄さの指摘(2-3)。イラストを描く
  ↓
Kaz: 指摘を見て直す → 貼り直し(何度でも)
  ↓
Kaz: 承認 → Claude が公開してデプロイ → 記録を更新
```

### 2-0. 新しい流れ(2026-10-05 から。Kaz が決定)

Kaz へのインタビューを軸に、記事を面白くする流れ。

1. **概要**: Claude が、テーマの概要と構成案を考える(2-1)
2. **質問**: その概要をもとに、Claude が Kaz への質問を考える(5〜8問。意見・好み・失敗・偏りを引き出す)
3. **インタビュー**: Kaz が質問に答える。答えは、personal-brain に記録し、提案ファイルに貼る(2-1b)
4. **記事化**: Claude が、答えを軸に、記事にまとめる。**元のテーマから逸れない**
5. **編集**: `manavillage-editor`(面白くするエージェント)に通す。事実と出典は変えない
6. **承認**: 編集後の記事を、Kaz が確認し、承認する
7. **公開**: 公開してデプロイする

- `manavillage-checker`(確認専用)は、既定では通さない(Kaz が頼んだときと、事実の記述が変わったときだけ)。**事実の確認は、省かない**: 提案のときに、出典を開いて確かめておく
- 面白くするとは、**事実を盛る・断定を強める**ことではない。Kaz の意見と見方を、前に出すこと

### 2-1. 提案(Claude が出す)

テーマの抽出は、これまでと同じ(`node scripts/pick-topic.mjs <english|japanese>` で在庫から無作為。重複や「勝てない」ものは `skip` にして引き直す)。

提案は `planning/proposals/<slug>.md`(日本語学習は `planning/japanese/proposals/`)に書き、要点をチャットに出す。**提案に書くこと**(順番や見出しの形は自由):

- 仮タイトルの案(2〜3個)、主キーワード、検索意図、想定読者(日本語学習はレベル)
- **使えそうな体験談の候補**(2-1b): 構成案の各見出しで、Kaz の体験談を入れられそうな所と、そこで使いたい体験
- **勝てる理由**: 主キーワードで実際に検索し、上位の記事は何か、何が足りないか(上位記事にない情報を、最低1つ)
- **概要**: 記事が読者に何を渡すか(3〜5行)
- **構成案**: 見出し(h2, h3)と、各見出しで言うこと。決まった型は使わない。**同じ科目の直近5本の見出しの流れと、似すぎないようにする**
- 各見出しで使えそうな具体例、例え話と小ネタの案(2-4)
- 根拠にできる出典(Claude が原典で確認済みの URL と、確認できた内容)。確認できなかったものは、そう書く
- サムネと本文の図の案
- 内部リンクの候補(公開済みの記事。いまは少ない)

Kaz は、これを素材として使う。使わない部分があってよい。

**2-1b. 体験談の候補と、Kaz への質問**(提案のときに、Claude が行う)

- 構成案で、体験談を入れたい所(「こんな体験があれば、読者に伝わる」)が出たら、**その体験が記録にあるか、検索する**: personal-brain(`search_persona`、theme: learning など)と `content/materials/`
- 記録に**ある**: 提案に、「この体験を使える」と、記録の内容を書く(記録にない細かい事実を足さない)
- 記録に**ない・足りない**: 作らずに、**Kaz に質問する**。形は、「〜な体験談を使いたいのですが、そういう体験はありませんでしたか?」。何のために使いたいか(どの見出し、何を伝えたいか)を一言そえる。Kaz が思い出して話してくれたら、それを使う
- **Kaz が話してくれた体験は、personal-brain に記録する**(`add_persona_entry`、kind: `event` か `insight`、theme: learning)。あとの記事で、検索して使えるようにする。数字や固有名詞は、Kaz が言ったとおりに残す
- Kaz が「ない」と答えたときは、その体験なしで構成を組み直す(体験の代わりに、確認できた出典や、一般的な例を使う)。**作り話で埋めない**

**2-1c. 体験談・意見が中心の記事の書き方**(2026-10-04 に Kaz が決定)

- **主張は1つに絞り、はっきり言い切る**。体験談の記事は、読者の背中を押す・元気づけるのが役目。主張を弱める言い方(「ただし研究では〜」「確認できていない」)を、本筋に混ぜない
- **研究の詳しい中身(数字、年齢差、限界)は、別の記事に回す**。体験談の記事には、主張を支える研究(確認できたもの)を、短く1つだけ入れてよい。「詳しくは、別の記事で解説します」と書き、**書くことのリスト(`inventory.csv`)に、その記事を入れる**
- ただし、**確認できていない主張を、事実のように書かない**。主張を弱めずに、書かない・別記事に回す、で対応する。研究が主張と食い違うとき(例: 「効く」と言いたいが、研究では示されていない)は、その研究を、本筋に出さない。**研究に支えられているかのような書き方もしない**
- **コラム(`class="voice"`)は、補足の読み物**。本文だけで話が完結し、コラムを抜いても通じるようにする。コラムは、題を付けて、単独でも読めるようにする。本文の言い換えにしない

**2-1d. 文章の書き方(読者を引きつける)**(2026-10-04 に Kaz が決定。3本の下書きへの指摘から)

- **見出しは、ラベルにしない**。「まとめ」「〜とは」「研究でわかっていること」「間違えやすい文」のような、中身の種類の名前は避ける。次の4つのどれかにする: **問い**(手を上げるのは、rise? raise?)、**意外性・ズレ**(1か月続けたのに、効果は感じなかった)、**読者の場面**(昇給をお願いするメール、どっちを書く?)、**約束**(「ずっと」を足すだけで見分けられる)。見出しだけを読んで、話が追えるようにする。同じ型を続けない。まとめの見出しは「今日、持って帰ってほしいこと」にする。見出しは目次(3つ以上で自動表示)としても読まれる
- **導入は、説明ではなく、場面か問いから**。読者がその場にいるような場面で始め、「その答えを今日つかもう」と持っていく
- **話の順序**は、「引っかかり → 少し考えさせる → 答え → 落とし穴 → 持ち帰り」。結論を先に書く型は使わない。間違い例は、最後にまとめず、途中の「ここで落とし穴」に入れる
- **口調と改行**: 1〜2文で改行し、大事な一言は1行で独立させる。読点(、)を減らし、短い文、問いかけ、ひとりごとのような一言を混ぜる。説明書きのような、同じ長さの文を続けない
- **説明は、具体例から**。用語は後から名付ける。たとえば自動詞・他動詞は、「ペンが立つ」と「ペンを立てる」(自分で動くか、だれかが動かすか。「リンゴを立つ」とは言わない)のような、身近な物の動きで見せ、日本語のペア(立つ/立てる、開く/開ける、上がる/上げる)を並べてから、英語につなぐ。見分け方も「〜を」を入れてみる、のようなテストにする
- **問いは、日常の体験から、1段ずつつなぐ**(2026-10-05 に Kaz が指摘。デカルトの記事で、問いに読者がついてこられなかった)。各見出しの問いの**直前**に、読者が「あるある」とうなずく**一般的な場面**を1つ置く。そこから「でも、よく考えると……」という引っかかりを出し、引っかかりが育ってから、問いを立てる。体験 → 引っかかり → 問い、の3段で、一気に飛ばない
  - 日常から離れた設定や専門用語(「全能の欺く者」「ステージングエリア」など)は、**橋をかけてから**出す。例: デカルトは、「夢の中で、夢だと気づけなかった経験」→「いまも夢ではないと言い切れるか」→「確かだと思うこと全部を疑ったら」と進め、そのあとで「欺く者」を出す
  - 場面は、**だれでも体験する一般的なもの**にする(友だちの後ろ姿を見間違えた、共有の資料が保存できなかった、など)。Kaz の体験として書かない(体験談は、記録があるものだけ)
- **読む気を削ぐ書き方をしない**(2026-10-05 に Kaz が指摘)。本文の途中に、**注釈の括弧書き**(「この記事の例は、考える入口として置いたものです」など)や、**断り書き**(「〜までを書いておきます」「確認できた範囲では」「これは私の推論です」など)を独立させて入れない。「我々は〜と考えます」のような、**堅くて不自然な言い回し**も使わない。話し言葉に近い、自然な文にする。根拠が確認できない主張は、断り書きで残さず、**書かない**か、別の記事に回す。出典の情報(だれの研究か、何件か)は、必要なときだけ、本文の流れの中で自然に出す
- 体験談を足すことはしない(雪菜の記事も、記録のない体験は書かない。口調と場面で、親近感を出す)

### 2-2. 執筆と、渡し方

- **既定では、Claude が書く**(2026-10-04 に Kaz が許可。Kaz は最終チェックをする)。Kaz が自分で書きたいときは、Kaz が明示する。以下の「貼る」の流れは、Kaz が書くときのもの

- Kaz が書く。分量・構成・文体は Kaz が決める(目安は科目の文書)
- **チャットに貼る**(リモートのセッションからでも渡せる)。貼るのは、本文(Markdown)と、使いたい題名。frontmatter は Claude が組み立てる
- 図を入れたい所には、`[図: こんな図が欲しい]` と書いておく(Claude が描く)
- 貼ったものを、Claude は `content/…/articles/<slug>.md` に `status: draft` で保存する。**言葉は変えない**。frontmatter の追加と、日本語学習のルビの記法への変換(2-3)だけを行い、変えた所を報告する

### 2-3. 確認(Claude)

Kaz が貼った文章に対して、次を行う。**どれも、指摘だけ。直した文は出さない。**

1. **機械チェック**: `node scripts/check-article.mjs <slug>`(frontmatter、見出し、タグ、内部リンク、ルビなど。何を見るかは科目の文書)
2. **事実・出典の確認**: 研究・統計・文法の説明を、原典で確かめる。確認できないもの、原典と違うものを、該当箇所と理由つきで指摘する
3. **読みやすさ・薄さの指摘**: わかりにくい所、抽象的な段落、削っても困らない段落、上位の記事や、すでに出した記事との重なりを、該当箇所と理由で指摘する。構成が、同じ科目の直近5本と似すぎていないかも見る
4. 返す形: 項目ごとに「該当箇所の最初の数語 — 何が、なぜ問題か」。重要度が高いもの(事実の誤り、確認できない主張)を先に出す
5. 確認は、**別のエージェント(`manavillage-checker`)**に任せる。Claude 本体が、Kaz の文章の評価を左右しないため

Kaz は、指摘のうち、直すものを選ぶ。**指摘に従う義務はない**(事実の誤りだけは、直すか、その主張を削る)。

### 2-4. 書くときの助言(提案と、指摘の基準)

Kaz が書くときの助言で、Claude が提案を出すときと、指摘をするときの基準にもなる。守る義務ではない。

- 導入は短く。最初の数行で、この記事で何が分かるかを示す
- 1つの主張に、具体例を1つ以上
- まとめで本文を繰り返さず、次にやることを示す
- 水増し(同じ主張の言い換え、長い前置き)をしない

**例え話**: 日常の場面(学校、通勤、コンビニ、スマホ、友達、家族、ご飯など)を使うと伝わりやすい。説明する仕組みと対応させる(手本:「一目ぼれした人より、毎日会う幼馴染のほうが覚えているよね？単語も一緒」)。1つの主張に1つ。たとえ話として書き、効果の裏付けのように見せない。特定の属性を揶揄しない。

**小ネタ**: 「何もない所で躓くことありますよね」のような、他愛のない共感は、事実でなくてよい。ただし、学習の成果の裏付け、数字、資格や経歴、実在の人物・店・商品の名前、誰かを傷つける話は、小ネタにしない。小ネタを主張の根拠にしない。

**運営者の体験**: Kaz 自身の体験談を、囲み(`<div class="voice">`)で書いてよい。Kaz が書くので、素材庫との照合はしない。数字や成果は、事実を書く。

### 2-5. イラスト(Claude が描く)

- **サムネ(核のイラスト)**: 記事ごとに1枚。記事の核の概念が、文章を読まなくても伝わる図。記事一覧のカードと共有画像に使われ、**記事ページでは、タイトルと本文の間に自動で表示される**(本文には書かない。書くと機械チェックが不合格にする)
- **本文のイラスト**: 枚数は決めない。Kaz が `[図: …]` と印を付けた所と、説明に図があると分かりやすい所に置く。飾りだけの絵は置かない
- 白い背景に、3歳児が描いたようなゆるい絵。画風はサイト全体で統一(`scripts/doodle.mjs`)。webp で軽く。`alt` に、図が伝える内容を書く
- 描いたら、チャットに画像を送る。Kaz が直してほしい所を言う

### 2-6. 公開

- Kaz が承認したら、Claude が `status: published` と `publishedAt` を書き、topic-map を `published` にし、デプロイする
- 完成した記事の `.md` と画像は、チャットに送ってよい(リモートのセッションでは localhost を開けない)

## 3. 技術的な SEO とタグ(サイト全体)

- sitemap は、公開済みの記事と、検索に出してよいタグページだけを含む。下書きは含めない
- 各記事に、canonical、OG タグ、JSON-LD(`BlogPosting`、`BreadcrumbList`)を出す
- タグページは、記事が3本未満のあいだ、またはハブ記事があるテーマでは `noindex`
- タグは分類のためのもの。科目ごとの一覧から選び、1記事に3〜5個。主キーワードをそのままタグにしない
- 掲示板: 返信ゼロのスレッドは `noindex`

## 5. キャラクター記事(白河雪菜)

2026-10-04 に、Kaz が決めた。**白河雪菜は、アンバサダー**。著者が二人いると面白いから、二人にする。Claude が雪菜になりきって、記事を書く。**雪菜が語る体験談は、Kaz の本当の体験がもと**(作り話はしない)。設定は `web/content/characters/shirakawa-yukina/profile.md`(確定版。案は `candidates.md`)。**英語学習(日本語で書く)と、日本語学習(英語で書く)の両方**で使う。

### 署名と、読者への伝え方

- 記事ごとに署名を分ける: Kaz が書いた記事は「Kaz」、雪菜の記事は「白河雪菜(アンバサダー)」。frontmatter の `author: kaz`(既定)/ `author: yukina` で決める
- 雪菜は、署名「白河雪菜(アンバサダー)」と、運営者ページの紹介で伝える(2026-10-05 に Kaz が決定。「架空のキャラクター」「実在の人物ではない」という説明や、体験談が Kaz の体験をもとにしていることは、読者向けには書かない)
- プロフィール(運営者ページ)に書くこと: 「白河雪菜は、まなビレッジのアンバサダーです」と、人柄(のんびり、ほめ上手、いっしょに続ける仲間)。**AI の関与は書かない**。体験談の出どころや、実在かどうかは書かない(2026-10-05 に Kaz が決定)
- 構造化データ(検索エンジン向けの著者情報)では、雪菜を実在の人物(`Person`)として載せない(組織の署名にする)

### 雪菜の記事の作り方

- 流れは、Kaz の記事と同じ形: 在庫から抽出 → 提案(体験談の候補と質問を含む)→ Kaz が選ぶ → **Claude が、雪菜の口調で書く** → 別のエージェント(`manavillage-checker`)が、事実・出典と、体験談の裏付けを確認 → Kaz が確認 → 承認 → 公開。**公開は、Kaz の承認後だけ**
- 口調と人柄は、`profile.md` に従う。科目の文書の書式も、Kaz の記事と同じ
- 体験談を使う記事は `type: experience`、使わない記事は `type: general`。囲みのラベルは「雪菜のストーリー」。`materialsUsed` には、使った体験の出どころ(personal-brain の記録、素材ファイルの節)を書く

### 体験談のルール(Kaz の記事も、雪菜の記事も、同じ)

- **体験談は、Kaz の本当の体験だけ**。personal-brain と `content/materials/` に記録があるものだけ使う。記録にない細かい事実(数字、時期、場所、人、気持ち)を、足さない
- 記録がないときは、書かずに、**Kaz に質問する**(2-1b)。Kaz が話した内容は、personal-brain に記録してから使う
- 雪菜は、Kaz の体験を、**雪菜の話として語り直す**(「私は〜しました」)。**語り直すときも、実際にあったことだけ**を語り、雪菜の年齢や経歴などの設定を、体験に足さない。雪菜に、経歴の設定は付けない
- 数字(点数、日数、冊数、順位)は、記録にあるものだけ。効果の主張(「これで伸びた」など)は、体験だけでなく、確認できた出典でも裏付ける

### 確認(別エージェント)で足す項目

- 雪菜の記事に出た体験談が、すべて personal-brain か `content/materials/` に記録されているか(1つずつ検索して確かめる)。記録にない事実が足されていないか
- 口調と人柄が、`profile.md` と合っているか。**日本語の記事では、女性らしい口調になっているか**(一人称は「私」、やわらかい語尾。「俺」「僕」「〜だぜ」「〜だろ」「〜しろよ」のような男性的・乱暴な言い方がないか。ことさら古風な女ことば(「〜わ」「〜かしら」)になっていないか)。**親近感**(読者への話しかけ、共感、説教になっていないか)があるか。英語の記事では、あたたかく話しかける調子になっているか
- 雪菜が実在の人物として読める書き方になっていないか(所属・学校・勤務先・年齢などの経歴が書かれていないか)
