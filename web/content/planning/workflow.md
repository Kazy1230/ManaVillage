# まなビレッジ 記事制作ワークフロー指示書

manavillage.online の記事を、品質を保ったまま継続的に作るための手順書。
Claude Code はこのファイルに従って、企画・執筆・チェックを行う。

---

## 0. 目的と大原則

- サイトのテーマは「学び合える場」。読者が「分かった」と感じる記事を作る。
- 目的は記事数を増やすことではなく、**他のサイトにない価値のある記事を、続けて出すこと**。
- Google のスケールドコンテンツ・スパム(低品質な大量生産)に該当する記事は作らない。
- ペース: **1日2本 = 英語学習1本と日本語学習1本**(2026-10-02 Kaz 決定)。品質に問題が出たら本数を減らす。
- 1本あたり **5000字を目安**にする。ただし、内容が足りないなら水増しせず、短くてよい。
- **1つの検索意図に、1記事**。同じ検索キーワード、同じ意図を狙う記事を、複数作らない(1章の「テーマ管理」を参照)。

### 絶対に守ること

1. **学習に関する体験談を捏造しない**。運営者(Kaz)の、学習の方法・成果・経歴に関する体験談は、素材庫(personal-brain と `content/materials/`)にあるものだけ使う。素材庫にない学習体験談は書かない。一方、他愛のない日常の小ネタ(3-4の「小ネタ体験談のルール」)は、事実でなくてよく、どんどん入れる。
2. 根拠のない断定をしない。研究や統計に言及するときは、出典を確認できたものだけ書く。確認できなければ、その主張は削る。
3. 自分が書いた記事を、自分でチェックしない。チェックは別のエージェント(別セッション)が行う。
4. 公開(デプロイ)は Kaz の承認後のみ。自動公開しない。

## 1. ディレクトリ構成

```
content/
  materials/        # personal-brain から書き出した素材のスナップショット(Kaz管理)
  planning/
    cards/          # 企画カード(2026-10-02 まで。いまは作らない)
    outlines/       # アウトライン(執筆直前に作る)
    topic-map.md    # テーマ管理表(どの記事が、どの検索意図を狙うか)
  articles/         # 記事本体(status: draft / published)
  illustrations/    # 記事ごとのイラスト
```

### 素材庫(personal-brain)の使い方

素材の一次ソースは、personal-brain(MCPサーバー)。

- **企画のとき**: `get_persona_core` で `recentThoughts` と `themeIndex` を確認する。`search_persona` を、テーマ(`learning` を中心に、必要なら `creative`、`work`)を指定して呼び、関連する考えや体験を取得する。
- **執筆の前**: 記事のテーマで `search_persona` を呼び、体験と意見を取得する。`get_persona_exemplars` で、Kazの文体サンプルを確認する。
- **`content/materials/`**: personal-brain から書き出したスナップショット。personal-brain に接続できない環境でも作業できるようにするためのもの。週次のテーマ選定のときに、Kaz が同期する。
- **検索して見つからない学習の体験談は使わない**。その場合は、一般的な内容で書く。
- **使ってよい素材**: 学習方法、英語学習の体験と考え方。恋愛、人間関係、お金、健康、仕事の愚痴など、学習と関係のない私的な内容は、記事に使わない。
- **個人の意見と一般的な事実を分ける**: 「マーカーは無駄」のような個人の方法論は、「運営者の意見・体験」として書く。「効果がある」と一般的に主張するときは、根拠を確認する。

### テーマ管理(topic-map)と、記事どうしの重複(カニバリ)対策

**なぜ管理するか**

- 同じ検索キーワード、同じ意図を狙う記事が複数あると、記事どうしが順位を奪い合い(カニバリ)、どれも上位に上がりにくくなる。ペナルティではないが、効果が薄まる。
- 記事が増えると、人間も Claude Code も、「もう書いたか」を覚えきれない。だから、`content/planning/topic-map.md` で管理する。

**topic-map に書くこと(記事ごとに1行)**

- ID、仮タイトル(公開後は実タイトルと slug)
- 主キーワード(この記事が狙う、ただ1つの検索語)
- 検索意図(何を知りたい人か)
- 想定読者
- type、状態、ハブ、近い記事

**状態**: `idea`(在庫) → `outlined` → `draft` → `published`

**更新のタイミング**

- カード作成時: 登録する(`card`)。作る前に、既存の行を読んで、被りを確認する。
- テーマを選んでアウトラインを作ったとき、下書き保存時、公開時: 状態を更新する。
- 記事を統合、削除したときは、行を更新し、旧URLから新URLへのリダイレクトを設定する。

**重複の判定基準**

- 見るのは、読者の設定ではなく、**検索意図が違うかどうか**。
- 判定の質問: 「Aの検索語で来た人が、Bを読んで満足するか」。
  - 満足する → 重複。統合するか、どちらかを作らない。
  - 満足しない → 別の記事にしてよい。
- 想定読者だけ変えて、検索語も、中身もほぼ同じ場合は、**別記事にしない**。
- 読者で分けてよいのは、読者によって、検索する言葉と、知りたいことが実際に違う場合(例: 「英単語 覚え方 社会人」と「英単語 覚え方 中学生」)。
- 重複しそうなときの対応: ① 統合する。② 主キーワードと検索意図を変えて、差別化する。③ 片方を予備に回す。

**テーマのまとまり(ハブ記事)**

- 近いテーマの記事は、無理に離さず、1つのまとまり(ハブ)として、内部リンクで結ぶ。
- ハブ記事は、まとまりの記事が3〜4本たまってから作る(例: 「英単語の覚え方」まとめ)。ハブから個別記事へ、個別記事からハブへ、リンクする。
- ハブ記事の主キーワードは、広めの語(例: 「英単語 覚え方」)。個別記事は、より具体的な語(例: 「英単語帳 回し方」)。

## 2. 記事の種類

| type | 内容 | 学習の体験談 | 小ネタ体験談 |
|---|---|---|---|
| `general` | 一般向けの、分かりやすい解説記事 | 入れない(無理に入れない) | 入れる |
| `experience` | 一般的な解説 + 運営者の学習体験談を混ぜた記事 | 素材庫にあるものだけ入れる | 入れる |

- 体験談は、サイト全体の口調を崩さないよう、「運営者の体験」という囲みやコラム枠で入れる。
- 「Kazです」「僕の学習メモ」のような、個人ブログに見える表現は使わない。
- 素材庫に学習の体験談の材料がない日は、`general` を2本にする(小ネタ体験談は、どちらの type にも入れる)。

## 3. 全体の流れ

```
[毎日] テーマを在庫から選ぶ。英語学習1本・日本語学習1本(Kaz の確認なし)
   ↓
[記事ごと] アウトライン作成 → 企画チェック → 本文とイラスト作成 → 本文チェック
   ↓
下書き保存(status: draft)
   ↓
[毎日] Kaz が完成した2本を確認 → 承認したものを公開(デプロイ)
   ↓
[ときどき] Search Console を確認 → 基準と在庫の点数を見直す
```

**Kaz が確認するのは、完成した記事だけ**(2026-10-02 決定)。テーマや企画カードの承認はしない。テーマの良し悪しは、企画チェック(別エージェント)が判定する。

### 3-1. テーマ選定(毎日。Kaz の確認なし)

- テーマは、**在庫**(`content/planning/inventory.csv`。日本語学習は `planning/japanese/inventory.csv`)の `status: idea` の行から選ぶ。在庫は、科目ごとに扱うべき項目を全部書き出したリストで、足りなければ在庫そのものを増やす(`.claude/skills/manavillage-weekly`)
  - 在庫の列: id、分類、層(似た言葉の4つの層)、主キーワード、読者、レベル、ハブ、需要(サジェストでの目安。2 = その語句がそのまま候補に出る、1 = その語句で始まる候補がある、0 = 候補なし)、状態、slug、メモ
  - 選んだテーマは `topic-map.md` に行を足して管理する(topic-map は、アウトライン以降に進んだ記事の表)。在庫の行は `status` を `selected` にし、`slug` を書く
- **勉強法のテーマは「テーマ × 読者」で広げる**。読者違いの記事を作ってよいのは、(1) 検索の言葉が実際に違い(サジェストにその組み合わせが出る)、(2) 中身が「使える時間・目的とゴール・使う教材・1日のスケジュール・つまずく場面」のうち3つ以上変わるときだけ。満たさなければ、元の記事に読者別の節を足す。読者違いの記事は、元の記事と互いにリンクする
- **似た言葉・フレーズは4つの層でカバーする**: ① 似た単語(see/look/watch)、② 機能の言い換え(依頼、断り、謝罪など、同じ目的を果たす言い方を並べる)、③ 丁寧さ・場面の違い(くだけた〜丁寧、話し言葉と書き言葉、確信度)、④ 母語からのずれ(「よろしく」は英語で? など)。記事は、検索の言葉で「機能のハブ(言い方の一覧)→ 2〜3語の比較 → 1つの言い方」に分け、互いにリンクする
- 在庫を増やすときの材料: Search Console の検索クエリ(Kaz が共有したとき)、検索サジェスト、検索結果の「他の人はこちらも質問」「関連する検索」、掲示板の質問、素材庫(personal-brain)
- **選ぶ順番**: 需要(検索されているか)、勝ちやすさ(上位が大手や公式で埋まっていないか)、在庫の穴埋め(ハブに足りない記事か)の順に見て、点数の高いものから選ぶ
- 選んだら、`topic-map.md` の状態を `outlined`(アウトライン作成時)に進める。企画カードは作らない(アウトラインがその役を兼ねる)
- 選ぶ前に、`topic-map.md` を読み、主キーワードと検索意図が被らないようにする(1章の「重複の判定基準」)

### 3-2. アウトライン作成(執筆の直前に1本ずつ)

企画エージェントが、在庫から選んだテーマを膨らませる。作る前に、`topic-map.md` を再確認する(カード承認後に、近い記事が公開されている可能性がある)。

- 見出し構成(h2, h3)
- 各セクションで使う具体例(例文、間違い例と正解例の対比、つまずく場面)
- 各セクションで使う、身近な例え(3-4の「例えのルール」に従う)
- 各セクションで使う、小ネタ体験談(3-4の「小ネタ体験談のルール」に従う)
- 上位記事にない情報の候補(最低1つ)
- 根拠にする研究や出典の候補(調べる予定のもの)
- 使う体験談(素材の出典を明記。personal-brain の statementId か、素材ファイル名)
- 核になるイラストの内容
- 内部リンク先(既存記事。`topic-map.md` のハブ記事と、同じまとまりの記事を含める)

### 3-3. 企画チェック(アウトラインの段階)

チェックエージェントが、下の項目で判定する。**1つでも不合格なら差し戻し。**

- [ ] 独自の切り口が、具体的に書かれているか
- [ ] 核になるイラストが決まっていて、それだけで概念が伝わるか
- [ ] `topic-map.md` の他の記事と、主キーワードと検索意図が被っていないか(基準は1章の「重複の判定基準」)
- [ ] 被る場合、「Aを検索した人が、Bを読んで満足するか」で判定し、統合するか、検索意図の違いを明確にしてあるか
- [ ] 「上位記事にない情報」の候補が、アウトラインに含まれているか
- [ ] 各主張に、具体例が最低1つ割り当てられているか
- [ ] 各セクションに、身近な例えの案があり、説明したい仕組みと対応しているか
- [ ] 体験談を使う場合、素材庫に該当する材料が実在するか
- [ ] 根拠として挙げた研究や出典を、確認する計画があるか

### 3-4. 本文とイラストの作成

執筆エージェントが、企画チェックに合格したアウトラインに沿って書く。

- 口調: 説教的でなく、人間らしく親しみやすい。読者に呼びかける形を使ってよい。
- 導入は短く。最初の数行で、「この記事で何が分かるか」を示す。
- 1つの主張に、最低1つの具体例を付ける。
- 最後のまとめで、本文の繰り返しをしない。次に何をすればよいかを示す。
- 水増しをしない。同じ主張の言い換え、長い前置きは書かない。

**例えのルール**

- 説明の例えには、誰にでもある、ありがちで親近感の湧く日常の場面を使う。専門知識や特別な経験がなくても、すぐ想像できるものにする。
- 場面の例: 学校、通学、通勤、コンビニ、スマホ、友達、家族、ご飯、部活、バイト、幼馴染など。
- 手本:「一目ぼれした人より、毎日会う幼馴染のほうが覚えているよね？単語も一緒」。
  - 対応関係は、単語 = 人、繰り返し触れる = 毎日会う、覚える = 覚えている。
  - 「1回の強い印象より、繰り返しの接触が記憶に残る」という、伝えたい仕組みと合っている。
- 例えは、説明したい仕組みと、きちんと対応させる。面白くても、仕組みが違う例えは使わない。
- 1つの主張に、例えは1つ。凝った例えを重ねない。
- 特定の属性(性別、国籍、職業など)を、揶揄したり、決めつけたりする例えは使わない。
- 例えは、たとえ話として書く。学習の実績や効果の裏付けのように見せない。
- 例えは、核になるイラストにも使ってよい(幼馴染と一目ぼれの図など)。

**小ネタ体験談のルール**

- 他愛のない、誰にでもある日常の場面は、**事実でなくてよい**。読者の共感を作るために、どんどん入れる。目安は、各セクションに1つ。
- 手本:「何もない所で躓くことありますよね」。
- 基本は、読者に呼びかける形(「〜ありますよね」「〜しがちじゃないですか?」)。軽い一人称(「私もやりがちです」)も使ってよい。
- **小ネタに使ってはいけないもの**:
  - 学習の成果や効果の裏付けになる話(「〜したら伸びた」など)。
  - 数字(点数、期間、語数、回数)。
  - 資格や経歴。
  - 実在の人物、店、商品の名前。
  - 誰かを傷つけたり、恥をかかせたりする話。
- 小ネタは、記事の主張の**根拠にしない**。主張の根拠は、素材庫の学習体験談か、確認できる出典だけ。
- 学習に関する体験(何をどうやって、どう伸びたか)は、小ネタではなく、素材庫にあるものだけ使う。

**イラストの方針**

- イラストは飾りではなく、**説明そのもの**にする。文章を読まなくても、核になる概念が伝わる図を1枚作る。
- 補助的な図は、必要なときだけ追加する。
- キャラクターと画風は、サイト全体で統一する(「まなビレッジのイラスト」と分かること)。
- 画像は webp、軽量にする。`alt` に、図が伝える内容を書く。

### 3-5. 本文チェック

チェックエージェントが、下の項目で判定する。**差し戻しは最大2回。** 2回で合格しなければ、その記事は Kaz に判断を仰ぐ。

**薄さのチェック**

- [ ] 上位記事に書かれていない情報が、最低1つあるか(何かを明記させる)
- [ ] 具体例(例文、失敗例、図解)が、主張ごとに最低1つあるか
- [ ] 段落を1つ削っても、読者が困らない箇所がないか(あれば削除を指示)
- [ ] 抽象論だけの段落がないか
- [ ] 構成が、検索上位の記事とそっくりでないか
- [ ] 例えが、身近でありがちな場面か。説明したい仕組みと、きちんと対応しているか
- [ ] 例えが、学習の実績や効果の裏付けのように書かれていないか

**事実のチェック**

- [ ] 文法、語法の説明に誤りがないか
- [ ] 研究や統計の主張に、確認できる出典があるか(確認できないものは削除)

**捏造のチェック**

- [ ] 学習に関する体験談(方法、成果、経歴、数字)が、すべて personal-brain または `content/materials/` に存在するか(実際に検索して確認する)
- [ ] 小ネタ体験談が、他愛のない日常の場面だけか(学習の成果や効果の裏付け、数字、資格や経歴、実在の固有名詞、人を傷つける話が入っていないか)
- [ ] 小ネタ体験談が、記事の主張の根拠として使われていないか
- [ ] 個人の意見や方法論が、一般的な事実のように書かれていないか(「運営者の意見・体験」として書かれているか)
- [ ] 学習と関係のない私的な内容(恋愛、人間関係、お金、健康など)が入っていないか

**SEO のチェック**

- [ ] frontmatter が、すべて埋まっているか(4章を参照)
- [ ] title と description が、記事ごとに固有か
- [ ] h1 が1つで、h2、h3 が階層になっているか
- [ ] イラストに、内容の伝わる alt があるか
- [ ] 内部リンクが、最低2本あるか
- [ ] 主キーワードが、title、h1、導入に入っているか
- [ ] `topic-map.md` の他の記事と、主キーワード、検索意図が被っていないか
- [ ] ハブ記事(あれば)と、同じまとまりの記事に、内部リンクが張られているか

### 3-6. 下書き保存とレビュー

- 合格した記事は、`status: draft` で `content/articles/` に保存する。
- `draft` の記事は、サイトの表示、sitemap、内部リンクの対象から除外する。
- Kaz が1日1回まとめて確認する。体験談入りの記事は、体験談の事実に間違いがないか、Kaz が特に確認する。
- 承認された記事だけ、`status: published` に変更してデプロイする。
- 公開したら、`topic-map.md` の状態を `published` に更新し、実タイトルと slug を記入する。

## 4. 記事テンプレート(frontmatter)

```yaml
---
title: ""              # 記事ごとに固有。検索意図が伝わる言葉を入れる
description: ""        # 記事ごとに固有。120字前後
slug: ""               # 短い英語のスラッグ
type: general          # general / experience
status: draft          # draft / published
publishedAt: ""
primaryKeyword: ""     # 主キーワード(この記事が狙う、ただ1つの検索語)。topic-map と一致させる
searchIntent: ""       # 検索意図(何を知りたい人か)
targetReader: ""       # 想定読者
hub: ""                # 所属するテーマのまとまり(topic-map のハブ名)
tags: []               # 分類用。既存のタグから選ぶ(5章のタグのルールを参照)
coreIllustration: ""   # 核になるイラストのファイル名
coreIllustrationAlt: "" # 核になるイラストのalt
related: []            # 内部リンク先のslug(最低2本)
sources: []            # 根拠にした出典
materialsUsed: []      # 使った素材の出典(personal-brainのstatementId、または素材ファイル名)。学習の体験談を使う場合は必須
---
```

## 5. 技術的な SEO の設定(サイト全体で1回実装)

- `sitemap.xml` を自動生成する。`status: published` の記事だけを含める。
- `robots.txt` を置く。
- 記事の本文は、SSG または SSR で、最初のHTMLに含める(クライアント側だけで描画しない)。
- 各記事に、`canonical`、OG タグ、JSON-LD(`BlogPosting`)を出力する。
- タグページは、所属する記事が3本未満のあいだ `noindex` にする。
- **タグのルール**(タグは、検索で狙うキーワードではなく、記事を分類するためのもの):
  - タグは、既存のものから選ぶ。新しいタグを作るときは、既存のタグと意味が重複しないか確認する(表記ゆれを作らない。例: 「単語」と「英単語」)。
  - 1記事に付けるタグは、3〜5個までにする。
  - ハブ記事があるテーマは、ハブ記事を検索に出す。同じテーマのタグページは、`noindex` のままにして、ハブ記事とタグページが、同じ検索語を奪い合わないようにする。
  - 記事の主キーワードを、そのままタグにしない(タグページと記事が、同じ語を狙ってしまうため)。
- 掲示板とコメント:
  - ユーザー投稿内のリンクに、`rel="ugc"` を付ける。
  - 中身の薄いスレッド(返信ゼロなど)は、`noindex` を検討する。

## 付録: manavillage.online での実装(サイト固有のメモ)

指示書の内容を、このサイトの仕組みに合わせたときの対応表。指示書と食い違う場合は、指示書を優先して、この付録を直す。

### 置き場所

| 指示書 | このサイト |
|---|---|
| `content/` | `web/content/`(Next.js のプロジェクトは `web/`) |
| `content/illustrations/` | `web/content/illustrations/<slug>/core.mjs`(描画コード)と `core.svg`(原本)。公開用の webp は `web/public/illustrations/<slug>/core.webp` に書き出す |
| チェックエージェント | `.claude/agents/manavillage-checker.md`(Claude Code のサブエージェント。執筆したセッションとは別に起動する) |

### コマンド(`web/` で実行)

- イラストの書き出し: `node scripts/illustrate.mjs <slug>` → `core.svg` と `public/illustrations/<slug>/core.webp` を作る
- 機械チェック: `node scripts/check-article.mjs <slug>` → 3-5 のうち、機械で判定できる項目(frontmatter、見出し、alt、内部リンク、タグ、主キーワード、topic-map との一致など)。不合格なら終了コード1
- ローカル確認: `npm run dev` → http://localhost:3000/articles/<slug>(下書きには「下書き」バッジが出る。本番では表示されない)

### frontmatter

- 4章のテンプレートどおりに書く。`coreIllustration` はファイル名だけ(例: `core.webp`)
- 追加のフィールド `hubTag`(任意): ハブ記事にだけ付ける。ここに書いたタグのタグページは、ハブ記事の公開後に `noindex` になる(5章)
- 旧形式の記事(`date` / `summary` / `draft` / `keyword`)も読める。書き直すときに新形式へ移す

### 本文の書き方

- h1 は title から自動で作られる。本文は `##` から始める
- 核のイラスト: `![alt と同じ文](/illustrations/<slug>/core.webp)`
- 例文ボックス: `<div class="example"><span class="lbl">EXAMPLE</span><span class="en">…</span><span class="ja">…</span></div>`(NG は `class="example ng"`)
- 運営者の体験(experience 記事のみ): `<div class="voice"><span class="lbl">運営者の体験</span><p>…</p></div>`
- 蛍光ペン: `==語句==`
- 内部リンク: `[記事タイトル](/articles/<slug>)`。公開済みの記事だけにリンクする
- リンクを張ると、その段落の直後に埋め込みカードが自動で出る(記事内で同じリンク先は最初の1回だけ)。1つの段落にリンクを詰めこむとカードが続いて読みにくくなるので、1段落のリンクは1〜2本までにする

### 5章の実装状況

- sitemap: 公開済みの記事と、検索に出してよいタグページだけを含む
- 記事ページ: canonical、OG タグ、JSON-LD(`BlogPosting`)を出力。下書きは `noindex`
- タグページ: 公開済みの記事が3本未満、または `hubTag` で指定されたハブ記事が公開済みなら `noindex`
- 掲示板: 返信ゼロのスレッドは `noindex`。コメントと書き込みはリンクに変換せず、テキストとして表示している(リンクを出すようにする場合は `rel="ugc"` を付ける)
